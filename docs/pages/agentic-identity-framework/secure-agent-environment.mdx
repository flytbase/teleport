The Teleport Agentic Identity framework introduces a multi-layered approach to
securely running agentic workloads, the **secure agent environment**. In this
approach, security is built into the system. Meaning AI agents have a limited
range of operations they are allowed to complete, with each operation subject to
auditing and access controls. 

The layers are:

- **Sandboxing:** Untrusted code is isolated and ephemeral, so there is minimal
  risk that it will interface with systems it is not supposed to.
- **Identity:** Each component of the system, including the end user, the
  agent's execution environment, and the agentic workload to execute, can
  prove itself to the system as a known, trusted subject.
- **Access controls:** Encoded in the identity is a list of operations and
  resources that the identity has access to, and the system checks access before
  allowing any operation to take place.
- **Audit:** Access controls associate each operation with an identity, allowing
  the system to construct logs of which identities performed which operations at
  different times.

## Sandboxing

The first layer of the secure agent environment is **sandboxing**. Agentic
workloads are untrusted. Since agentic output is indeterministic, we must assume
that any code an agent executes is arbitrary. As a result, the only truly secure
way to protect a system against abuse by an agent is to isolate the agent from
the system.

As the first layer, sandboxing ensures that the agentic workload has no effect
on the surrounding system unless other parts of the system let it escape the
sandbox.

There are two components to sandboxing. The first is hardware isolation. In the
secure agent environment, we recommend hardware-level virtualization, e.g., a
Type 1 hypervisor, for running agent workloads. The agent has no access to an
operating system, so there is no attack surface on other software running in
your environment.

The second component is ephemerality. We recommend placing a time to live on
the virtual machine that runs agentic workloads. This way, the untrusted code is
isolated in time: it exists only as long as it is needed, and not long enough
for unintended side effects to take hold.

## Identity

The **identity** layer of the secure agent environment is consistent with
Teleport's overall approach to infrastructure: every human and non-human
component of the system receives an identity. That way, every component that
interacts with it can perform authentication and authorization checks on the
identity. 

For example, we recommend distributing identities to end users, the execution
environment for the agentic workload, and the agentic workload itself, in
addition to infrastructure components such as Kubernetes clusters, databases,
and web applications.

Once the agentic workload has an identity, other components can verify that
identity. A database, for example, can verify that the agentic workload is a
trusted part of the system and not a rogue actor.

For agentic workloads, it is crucial that the system associate the workload with
the human user that initiated it. There must be no way for human users to
conceal themselves by running agentic workloads.

## Access controls

In the secure agent environment, **access controls** take advantage of the
identity layer to enable components that interact with the agentic workload to
allow or deny operations. Because of the sandboxing layer, the agentic workload
has no default ability to operate on other components. If an operation is to
succeed, a component must explicitly allow it.

If every component of the system already has an identity, the system can encode
in each identity the permissions each component has to interact with other
components. Since end users have identities as well, the system can check
whether the end user has permissions to manage agentic workloads before running
them in the secure environment. In addition, infrastructure components in the
environment can check whether the agentic workload can operate on them before
allowing those operations.

## Audit

The final layer of the secure agent environment is **auditing**. Auditing allows
administrators to track the operations that an AI agent has performed in a
system so they can identity potential threats and investigate security breaches.

In the secure agent environment, sandboxing, identity, and access controls make
it straightforward to implement auditing. With sandboxing, the agent has no way
to interact with its environment unless the system allows specific operations,
which need to go through parts of the system that check the agent's identity in
order to implement access controls. Since these parts of the system already are
aware of the agent's identity and the operations it is attempting, an auditing
system only needs to emit telemetry that includes this information.

## Reference implementation

Teleport has implemented the secure agent environment in Teleport Beams. Beams
allows you to run agentic workloads securely on Teleport-managed infrastructure.
A beam is a remote environment for running an untrusted workload, designed for
AI agents. Each beam has the following components:

### Sandboxing

A beam runs on a Firecracker virtual machine with a time to live
of under 24 hours. An instance of `tbot` runs on the virtual machine, and
connects to a Teleport cluster via an SSH reverse tunnel. The `tbot` instance
runs Teleport VNet, setting up a TUN interface on the VM. The agentic workload
queries the VNet instance as its DNS resolver, and VNet returns the public
addresses of Teleport protected resources in your infrastructure. 

From the point of view of the agentic workload, it can attempt a connection to
any Teleport-protected resource. However, each connection to an infrastructure
resource must go through the Teleport Proxy Service and Teleport Agents
protecting the resource. The agentic workload remains isolated from its
environment but for its connection to Teleport-controlled proxy servers.

Since Teleport-managed infrastructure tears down the virtual machine after the
TTL, we can minimize the risk of the agent finding and exploiting
vulnerabilities.

### Identity

Every component of Teleport Beams has its own identity. As in any Teleport
deployment the Auth Service maintains several certificate authorities that it
uses to issue certificates to end users and Teleport services. In the case of
Beams, the following components receive certificates (in addition to Teleport
Agents and end users):

- The `tbot` instance running on the Firecracker VM
- The agentic workload (Workload Identity SVID)
- The Firecracker VM (SSH host certificate)

`tbot` issues a **delegated identity** to the agentic workload. The workload
receives certificates with the same subject information as the end user who
initialized the beam, including the user's login and Teleport roles.

The `tbot` instance periodically retrieves new certificates from the Teleport
Auth Service for each Beams component on the VM. When the agentic workload
attempts to authenticate to a Teleport-protected resource, it presents its
Teleport-issued certificate for validation against an Auth Service CA.

### Access controls

Because an agentic workload running on a beam must use Teleport-controlled
infrastructure to connect to resources outside the sandbox, and receives a
Teleport-issued identity, the Teleport-controlled infrastructure can execute
access controls. Teleport Agents inspect the certificate issued to the agentic
workload just as they do with any Teleport-issued certificate. From the
perspective of the agent, the certificate could be that of a human user or the
delegated agentic identity.

### Auditing

Components of a Teleport cluster emit audit events by sending a message to the
gRPC API on the Teleport Auth Service. Teleport Agents emit audit events
throughout the lifecycle of a session with a Teleport-protected resource, from
an authentication attempt to activity within the session and the closure of the
connection. Because Teleport Agents handle the agentic workload's certificate as
they would any user certificate, Beams has auditing built in. 

And because `tbot` issues a delegated certificate with the subject information
of the originalting user, auditors can see which users are managing which
agentic operations, and these workloads cannot hide behind anonymous logins.
